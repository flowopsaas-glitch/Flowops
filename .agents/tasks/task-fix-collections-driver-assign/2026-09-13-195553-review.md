# Wire the Collections command center to real driver assign/release/workflow endpoints (v1)

The Collections command center in the frontend was calling a spread of routes that never existed (`collection-ops/*`, `drivers/available`, `drivers/assign`, `collections-state-sync/auto-assign|release|workflow`), and one release path threw synchronously with no `try/catch` — a courier's first click on assign or release could surface a raw error. This change adds three tenant-scoped endpoints to the existing collections resource (`POST /collections/:id/assign-driver`, `POST /collections/:id/release-driver`, `GET /collections/:id/workflow`) with no Prisma schema change, and rewires `Collections.tsx` so every driver action hits a route that now exists, stripping the layered fallbacks and one block of unreachable code. Remaining lower-priority audit hits (dead components, legacy workflow-builder API, a stale owner-login helper) were verified and documented as intentional leave-alones in AUDIT-NOTES.md rather than patched with speculative backends.

Watch for: the `assign-driver` endpoint accepts any driver in the tenant regardless of `status`/`isActive`, so a manual assign can attach an OFFLINE or deactivated driver (likely by design for manual override — but worth a conscious confirmation before first customer). Everything else traced clean end to end.

**Verdict**: APPROVED

## High-level view

The three new endpoints reuse the established `findOne(id, companyId)` ownership guard, so every read and write is tenant-scoped like the pre-existing collection routes. `assignDriver` additionally re-validates that the target driver belongs to the caller's company before writing, closing the cross-tenant assignment gap.

The status machine is conservative against the real `CollectionStatus` enum: assign forces `ASSIGNED`, release clears the driver and only rolls `ASSIGNED → PENDING`, deliberately leaving `IN_PROGRESS`/`COLLECTED` untouched so a release can't rewind a collection that has already moved downstream.

The workflow read model references only fields and the one relation that actually exist on `Collection` (`driver`, `clientName`, `pickupAddress`, `status`), returning `null`/`[]` placeholders for the dispatch/pod/invoice sub-objects the drawer optionally renders. No non-existent relation is touched.

On the frontend, the fallback ladders collapse to single calls matching the new route signatures, and `autoAssignDriver` reads `suggestion.id` from the existing `suggest-driver` response — a shape that matches what that endpoint returns. The dead route strings are gone; the `collections-state-sync/*` calls that remain (dashboard, records, bulk-sync, sync, suggest-driver) are real, pre-existing routes and out of scope.

<summary>Details</summary>

### Tenant scoping and the driver-ownership check

All three service methods open with `await this.findOne(id, companyId)` (a `findFirst` on `{ id, companyId }` that throws `NotFoundException` for a foreign collection), and the controller feeds `companyId` from `@CurrentUser()`, never from the path. `assignDriver` goes one step further and re-queries the driver with `findFirst({ where: { id: driverId, companyId } })`, so a caller cannot attach a driver from another tenant by passing a foreign `driverId` — the write is refused with `NotFoundException('Driver not found')` before any update runs.

### Status transitions and the availability gap

`CollectionStatus` is `PENDING | ASSIGNED | IN_PROGRESS | COLLECTED | FAILED | CANCELLED`, so both writes use legal values. Release is the careful one:

```
release-driver:
  driverId := null   (always)
  status   := PENDING  ONLY IF current status == ASSIGNED
             (otherwise status is left as-is)
```

Releasing a driver from a collection that has already progressed to `IN_PROGRESS` or `COLLECTED` clears the driver reference without rewinding the lifecycle, so a stray release click can't resurrect completed work as pending.

The gap is on assign: `assignDriver` checks tenant ownership but not driver availability. The `/drivers?status=AVAILABLE` list and the `suggest-driver` suggestion both feed *available* drivers into the UI, but the endpoint will assign an OFFLINE or `isActive: false` driver if such a `driverId` reaches it (e.g. from a stale drawer or the `drivers[0]` fallback in `autoAssignDriver`). Likely intended as a manual override — dispatch sometimes needs to assign whoever they know is coming on shift — but it's worth an explicit decision before the first paying customer rather than an accident.

### Workflow read model — honest about missing relations

`Collection` has exactly one driver relation and no dispatch/pod/invoice/shipment relations, so `getWorkflow` returns those as literal `null` and `nextActions` as `[]`, populating only what exists:

```
collection.{id, reference:=id, customerName:=clientName,
            destination:=pickupAddress, syncHealth:=status,
            driverName, driverId}
driver | null   (id, name, vehicleType)
dispatch/shipment/pod/invoice := null
```

`openLinkedWorkflow` reads `workflowRes.data` defensively (`|| {}`, optional chaining throughout `resolveCollectionTruth`), so the null placeholders don't break rendering. `destination` being sourced from `pickupAddress` is a mislabel — it's the pickup location, not a delivery destination — cosmetic today since the drawer only displays the string.

### Frontend rewiring and the suggestion shape

The three action functions collapsed from nested `try/catch` ladders (including a `release` branch with a `requestLiveRefresh()` line stranded after a `return`) down to single calls against the new routes. `autoAssignDriver` derives its driver from `getSuggestedDriver()` and reads `suggested?.suggestion?.id` — the `suggest-driver` endpoint returns `{ suggestion, candidates }`, so this key path is correct, and it falls back to `drivers[0]?.id` then throws a descriptive `Error("No available driver to assign")` when nothing is available, replacing the old silent failure. The recommendation-display mapping later in `openLinkedWorkflow` (`suggestion?.recommendedDriver` / `?.driver` / `?.id`) does not match the `{ suggestion }` shape, but those lines are unchanged by this PR — pre-existing and out of scope.

### Leave-alone decisions (FEAT-003)

The AUDIT-NOTES.md verdicts hold up against the code: `LeadCapture` and `ReceivingQueue` are unmounted (no importers), the `workflowApi`/`memoryApi` consumers live under unrouted `CreateWorkflow/*` scaffolding, and `api/owner.ts` is a fully dead module (live owner login is `authApi.ts` → `POST /auth/owner-login`). `addressBookApi.markUsed` swallows its error with `.catch(() => {})`, so a missing route there can't surface to a user. None of these are reachable by a courier on first run, so leaving them untouched does not leave anything user-facing broken.

### Not tested

No automated tests were added or run — the sandbox has no node/npm and the owner builds via Docker on a VPS, so verification here is static only. Untested behaviorally: the assign→release→reassign status cycle, the cross-tenant driver rejection path, and the workflow drawer rendering against the minimal read model. These are the paths a first customer will exercise immediately; a manual smoke test of assign/release/open-workflow against a seeded tenant before go-live is worth the few minutes.
